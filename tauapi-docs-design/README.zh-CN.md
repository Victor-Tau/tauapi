# TauAPI 文档管理体系设计

设计日期：2026-11-06。审查基线：`ebc4cebd9c7edee2743700310fd877984ed349eb`，本次已核对与远端 HEAD 一致。

## 1. 建议采用的体系

建议把文档做成 AI 的工作入口：**短规则入口 → 按任务选路 → 相关领域和契约 → 源码与测试 → 变更记录 → 自动检查**。

AI 使用的规则、索引、技术契约、工作步骤、任务记录全部用英文。人看的项目介绍、操作说明、发布说明和交接总结全部用简体中文，写清楚“做什么、有什么影响、遇到问题怎么办”。中文说明不需要逐段翻译英文技术文档。

文档负责说明应该遵守什么、去哪里找；程序检查负责验证提交结果。两部分要一起建立。写上 MUST、让 AI 勾选“已阅读”，都不能证明它理解或执行了规则。

本包是设计和实施材料，不是已经接入仓库的系统。`examples/` 中的文件是示例，不能整包覆盖仓库。英文 `IMPLEMENTATION.md` 给出了迁移顺序和验收标准。

## 2. 当前项目的实际情况

当前是一个 Git 仓库，包含 `tauapi-fe/`、`tauapi-be/`、`tauapi-ops/`。前后端仍然独立构建、发布和回滚，构建脚本用 `git archive <commit>:<subdir>` 导出一个子树。文档要同时表达“代码在一个仓库”和“产物分开发布”这两件事。[仓库说明](https://github.com/Victor-Tau/tauapi/blob/ebc4cebd9c7edee2743700310fd877984ed349eb/README.md)

已有不少可用基础：根规则、系统地图、认证说明、详细计费约束、路由 JSON、部署脚本、测试、历史验收记录。优先整理这些内容，再补缺口。

| 当前问题 | 对 AI 维护的影响 | 首批处理方式 |
| --- | --- | --- |
| 根规则要求 AI 读中文 `map.md`，局部规则仍引用 `web/` | 语言分工与路径导航不一致 | 新建英文入口，更新当前路径，保留中文地图给人看 |
| `PLAN.md` 引用仓库中不存在的 `GOAL.md`，且仍保留三仓库阶段 | 旧计划会被误当成当前规则 | 归档原建设计划，标明已被 monorepo 决策取代 |
| 子目录的 CLAUDE 规则仍是上游内容，运维没有局部规则入口 | 从不同目录启动会得到不同且不完整的提示 | 根和三个分区建立短适配入口 |
| 根没有 `.github/workflows/`，现有工作流位于后端子目录 | 不能把这些文件当成当前 monorepo 的自动合并检查 | 建立根工作流，正确设置各工作目录 |
| 后端有三个 Go module，部分数据库测试会跳过 | 单个成功退出码不能证明所有必需检查完成 | 复用 `make test`，数据库任务另设真实三库检查 |
| 新机部署说明提前使用 `--with-slave`，脚本要求先完成初始化 | AI 照文档执行会卡在前置条件 | 校正顺序，单独记录“静态核对”和“完整演练” |
| 前端兼容字段只打印日志，后端回滚读取的 `schema_changed` 未写入发布记录 | 文字上的防护还不是程序门禁 | 建立发布元数据契约，再接入实际拒绝条件 |
| `STATUS.md`、验收记录和部署 JSON 都有历史时间 | 容易把当时通过当成现在通过 | 历史证据与当前观测分开 |

后四项属于文档与执行不一致的发现，不代表本次验证了线上状态。具体源码证据在 `audit/REPOSITORY_AUDIT.md`。

## 3. 文档层级

| 层级 | 推荐文件 | 只解决什么问题 | 何时读 |
| --- | --- | --- | --- |
| 全局入口 | 根 `CLAUDE.md`、`AGENTS.md` | 全局约束、定位方法、交付标准 | 每次启动、恢复任务 |
| 总导航 | `docs/ai/INDEX.md`、`REPOSITORY_MAP.md` | 任务属于哪个领域，下一步读哪一份 | 接到任务、范围扩大 |
| 分区入口 | 三个分区的 `AGENTS.md`、`docs/ai/INDEX.md` | 本分区边界、命令位置、局部规范 | 进入相关分区 |
| 领域说明 | 各分区 `docs/ai/modules/*.md` | 业务调用链、入口文件、常见故障、测试位置 | 修改该领域 |
| 跨目录契约 | `docs/ai/contracts/*.md` | 两个或多个模块必须共同遵守的行为 | 修改相关行为 |
| 工作步骤 | `docs/ai/workflows/*.md`、运维 runbooks | 功能开发、排错、升级、部署的执行顺序 | 对应任务 |
| 决策和工作记录 | `docs/ai/decisions/`、`docs/ai/changes/` | 为什么这样做、这次做到哪里、有什么证据 | 有关决定或长任务恢复 |

根规则建议控制在 80–120 行；分区入口控制在 60–120 行；模块卡通常 100–180 行。它们是维护目标，不是平台硬限制。超过篇幅时，把专题拆成按需阅读的文档。不要为了满足行数删掉关键约束。

普通任务的首次阅读应控制在少量文件内。先定位，再深入；任务范围扩大后补读。没有必要每次改按钮都读取部署历史和全部计费规则。

## 5. 哪份文件说了算

不能简单规定“代码永远覆盖文档”，否则 AI 会把实现错误写成新的规则。也不能让过时文档压过实际代码。应按问题区分事实来源。

| 要回答的问题 | 应读取的来源 |
| --- | --- |
| 系统应该如何工作 | 当前有效的契约、已采纳的架构决定、用户本次要求 |
| 当前代码实际上如何工作 | 当前提交的源码、可复现测试 |
| 当前线上运行什么 | 带时间、环境和命令来源的现场观测，以及对应发布记录 |
| 如何进行一项操作 | 有效操作手册和它调用的脚本，两者须一致 |
| 过去做过什么 | 固定版本的验收与变更记录 |
| 这次任务做到哪里 | 当前任务记录和对应分支的真实 diff |

每份正式 AI 文档登记类型、状态、负责领域、源码入口和验证依据。状态用 `active`、`draft`、`historical`、`superseded`、`deprecated`；是否生成用独立字段表示。`reviewed_at` 不能每次提交自动刷新，只有真正核对来源时才更新。

发现文档与代码冲突时，记录差异、判断原本意图、增加或运行能区分正确行为的检查，再修复代码或文档。没有依据时明确标成未知；不能删除测试或放宽约束让结果看起来一致。

## 6. 优先建立的跨目录契约

### 路由与同源访问

继续保留 `tauapi-ops/ROUTE_CONTRACT.json` 作为分流数据源。英文说明只解释规则、例外、验证方法，不再维护一张重复的完整路由表。

必须说明 SPA 页与 API 的区别、`/dashboard/billing/` 对 `/dashboard` 的优先级、未知 API 的 JSON 404、插件路径、保留命名空间、同源相对 URL。新增页面要同时检查浏览器导航和直接刷新。

现有生成器的插件检查依赖显式参数，且只扫描字面路径；它不能证明全部动态插件路由都正确。完整路由验证还需要真实路由清单或启动后的注册表，以及隔离环境中的请求检查。

### 认证与权限

区分控制台会话、PAT、relay API key。覆盖 JWT、refresh cookie、轮换与并发、撤销、Origin 校验、后端权限、跨节点缓存。新增控制台接口必须处理 PAT 路由策略，不能只在前端隐藏按钮。

现有中文认证技术说明内容较完整，应逐条迁移为英文技术契约，并保留源码与测试依据。中文人类说明只需讲如何登录、会话何时失效、常见问题怎么判断。

### 计费与额度

迁移时逐条保留 `.agents/rules/billing.md` 的约束。至少包括参数上限、透传绕过路径、数值转换和溢出、预扣、最终结算、退款、图像计数、流中断和异步任务竞争。

前端表达式样本是后端契约的副本。指定后端样本为来源，同步脚本负责复制和记录 hash，CI 比较两端是否一致。两端独立构建仍只读取自己的子树。

上游导入的 hash 和本地修改后的契约 hash 分开保存，不能修改 `UPSTREAM.json` 来掩盖本地改动。副本一致后，还要运行两端各自的语义测试。

### 插件协议

插件 Markdown、JSON Schema、TypeScript 定义和宿主测试要一起维护。说明 native routes 与 host protocols 的差别，以及 usage、轮询、失败和退款语义。每个插件不再散落一套说明书。

### 前端发布

说明版本化资源、HTML 和元数据缓存、丢失资源 404、旧标签页保留、更新提示和回滚行为。兼容性要使用明确的协议版本、能力或支持列表；commit hash 不能自然地当版本大小比较。

### 后端发布与数据库

说明 master/slave 的职责、连接排空、退出码 10 的暂停状态、混合版本兼容、schema 变化和回滚前提。应用回滚和数据库恢复分开。

发布记录中的 schema 兼容性未知时，应保持未知并阻止不安全回滚，不能把字段缺失默认为没有变更。先确定元数据来源和实际校验方式，再让文档声称具备自动保护。

所有回滚入口都应复用同一个校验，包括 `deploy-backend.sh --rollback`，避免只修复外层脚本却保留另一条绕过路径。

## 7. 模块卡怎么写

每张卡只写九项：职责、边界、入口文件和符号、调用链、输入输出、使用的契约、关键不变量、验证入口、变更联动。

后端先建认证、relay、计费、插件、数据库、独立库六个入口。前端先建路由与外壳、认证、数据请求、共享组件与主题、计费展示五个入口。运维先建路由、前端发布、后端发布、备份恢复、上游同步五个入口。其余业务按实际任务补充。

说明具体到文件与符号，但不抄整段源码、不复制依赖版本清单、不依赖容易漂移的行号。调试提示用“症状—检查入口—如何区分原因”的形式。

## 8. AI 每次任务的流程

1. 确认仓库根、分支、已有改动和用户要求，读取全局入口。
2. 由任务语义和预计文件路径选取领域，读对应模块卡与契约。
3. 查看相关源码和现有测试；先查已有实现，再决定改哪里。
4. 写一份简短任务记录：目标、范围、关键约束、验证计划、文档影响。
5. 修改后用实际 diff 再次路由，发现新增影响就补读、补验证。
6. 执行适用检查，明确记录 `passed`、`failed`、`skipped`、`blocked`、`not_run`。
7. 同步受影响文档；没有文档影响时写出理由，不制造无意义修改。
8. 检查最终提交对应的 CI 结果，更新任务结论，用中文向人说明改变与限制。

任务文件可以记录“上次已验证的提交”，但不能要求它包含自己的最终提交号。准备好后标为 `ready_for_ci`，是否验证通过由外部 CI 结果决定。后续归档提交引用已验证的实现版本，并运行自己的文档检查，避免“记录测试结果又产生新提交”的循环。

小修复只需简短记录，不强制一套多文件计划。跨组件、数据库、发布、上游升级或跨会话任务，需要完整恢复信息。提交说明和机器证据可以英文；给用户看的总结用中文。

任务记录应保存未完成检查、已排除假设、下一步动作和恢复命令。不能保存思维过程、整段聊天、密钥或完整生产数据。恢复时重新查看实际 diff，不盲信上个会话写的“完成”。

多代理任务应明确各自负责路径，附必读文件、约束和证据要求。主代理在合并后重新计算影响范围。给每个任务独立记录，避免多个代理共同覆盖一个全局 `STATUS.md`。

## 9. 如何自动检查

### 文档本身

检查链接与源码路径、文档 ID、状态、归属、命令工作目录、生成结果是否最新；禁止有效入口指向归档记录作为当前规则。英文和中文以文件用途检查，允许命令、标识符、引用文本及保留的上游原件例外。

### 文档与代码的联动

登记表按任务语义、预计路径和实际 diff 的并集匹配。多个领域可以同时命中。新增源码必须有分区归属；无法分类的改动转入总览判断，不能静默跳过检查。

每份受影响契约都要有处理结论：已更新，或已核对且行为未变及理由。不能只检查“有没有改一份 Markdown”，也不能把 AI 的理由当成测试替代品。

### 真实验证

| 改动范围 | 检查要求 |
| --- | --- |
| 后端 | 受影响回归；需要全套时使用 `tauapi-be` 下的 `make test`，覆盖三个 module |
| 数据库 | 真实 SQLite、MySQL、PostgreSQL；新库、升级、重复启动，缺 DSN 不能算通过 |
| 前端 | 相关 Vitest、typecheck、构建；lint 对新问题实行零新增 |
| 路由 | 生成配置、页面刷新、API JSON 404、特殊例外、插件边界 |
| 计费 | 上下限、无效数值、预扣/结算/退款、图像与异步任务用例、两端样本一致 |
| 发布 | 独立子树构建、版本兼容、回滚前提；按变更风险在隔离环境演练 |

旧 lint 问题应重跑确认后建立带规则、文件、位置特征、工具版本的基线；不能只比较总数，更不能在新任务中自动扩张豁免。已解决项从基线删除。禁止通过关闭规则获得绿色结果。

验证结果应绑定最终候选提交或明确的源文件摘要。CI 把提交、命令、工作目录、工具版本、结果、跳过原因、证据地址写入产物。失败、日志缺失和无法运行都不能变成成功。

### Claude 提示与最终门禁

根及分区 `CLAUDE.md` 使用显式 `@AGENTS.md`；大文档使用普通链接按需读。采用前确认实际 Claude Code 版本和加载结果，避免只凭某个版本的默认行为。

自动维护的启动程序统一在 Git 仓库根启动 Claude。若直接从子目录启动，要验证祖先规则是否加载及导入信任行为；同目录 `@AGENTS.md` 并不自动保证所有启动位置都无需外部导入确认。

SessionStart 用来提示恢复入口；PreToolUse 用来及早提示或拦住已知违规操作；Stop 检查是否漏掉交付项并设置有限重试。项目 hooks 可能被改动或关闭，所以最终是否合并、是否发布由独立 CI 和权限控制决定。

根工作流与分支规则需要真正接通。CI 脚本被同一变更修改时也要审查检查器本身；不能因为 AI 同时改了规则和结果就视为验证。正常任务可自动修复、重新检查；只有缺少业务决定、必要凭据或影响不可逆且未授权时才交给人处理。

## 10. 生命周期和双语维护

每个约束有一个有效归属。跨文档引用统一 ID，例如 `AUTH-001`、`BILL-004`；同一段规则不复制到全局入口、分区入口和模块卡三处。

架构决定写明背景、选择、代价、状态和 `supersedes`。新决定取代旧决定，旧记录保留历史。普通修复不需要新增 ADR；影响接口、数据模型、依赖边界、发布策略时才需要。

中文说明通过 `related_ai_docs` 或登记表关联英文来源。涉及人的操作、页面行为或发布影响时同步中文；内部函数重命名不用强制双语改一遍。检查器可以发现关联来源发生变化并要求确认，不能自动证明翻译正确。

已有 LICENSE、NOTICE、多语言上游 README、UI 语言包和需要原样保留的上游文件保持原样；它们标注来源和用途，不作为新的 AI 规则入口。有效英文指南需要完整承接相应约束。保留原件不等于继续强制 AI 读取中文技术说明。

日常维护分三种触发：每次改动检查文档影响；每次上游升级检查入口规则和跨组件契约；定期自动检查死链、失效路径、过期例外和没有解决的文档差异。定期检查可以列出问题，不能只更新日期就宣称重新验证。精简结论长期保存在 Git，大日志与图片保存为独立证据并记录保留期限。

## 11. 分四批落地

**第一批：修正入口和事实。** 建立根及分区适配文件、英文地图、语言与文档状态规则；标记旧计划；修正 `web/` 和拆仓叙述。逐条迁移已有强约束，保存来源清单。

**第二批：建立最关键的契约。** 先补路由、认证、计费、插件、前端发布、后端发布与数据库；建立少量领域卡。把部署顺序、兼容性日志、schema 元数据缺口写成明确的跟进事项，不声称文字已修复代码。

**第三批：接上程序检查。** 实现登记表 schema、路径/链接/归属校验、生成导航、变更影响检查；根 CI 执行前后端与跨组件检查；解决必需数据库测试静默跳过的问题。

**第四批：验证 AI 是否会按这套体系工作。** 用新增页面、refresh 故障、计费数量错误、数据库字段、上游升级五种任务演练。从仓库根、各分区和恢复会话启动，检查能否定位、补读、运行正确检查并留下准确证据。

部署脚本和业务代码的实际修复应各自形成可验证改动。文档整理可以先完成，不能靠把缺口写进文档就把缺口标为已解决。

## 12. 验收标准

体系完成后应能逐项回答：

- 新会话从根目录或三个分区启动，都能获得同一套全局约束和适用局部规则。
- 活跃文档没有死链、无效源码入口、无归属文件或相互矛盾的当前状态。
- 常见任务能通过少量入口找到相关源码、测试和跨组件契约。
- 计费、认证、数据库和发布等原有强约束没有在迁移中丢失。
- 新页面漏改路由、修改计费样本不同步、必需数据库测试缺 DSN 等负面案例会使检查失败。
- 历史验收不再充当本次完成证明，发布兼容性未知不会自动当作安全。
- 已完成任务有对应版本和真实证据；未完成工作有可恢复的下一步。
- 人只看中文说明就能理解改了什么、影响什么、需要自己做什么。

文档体系验收与发布脚本修复分别记录。前者要求准确暴露未知兼容性并保留跟进项；后者要在实际代码修复后，证明所有发布或回滚入口都会按要求拒绝不安全操作。

## 文件使用方法

`IMPLEMENTATION.md` 是交给 Claude Code 的英文实施说明；`audit/` 是本次审查依据；`examples/` 是结构和规则示例；`templates/` 是文档模板；`ACCEPTANCE.md` 是实施后的验收清单。先让 Claude Code读取实施说明，在当前最新代码上复核基线，再按阶段落地。

本次审查只核对了仓库与官方机制资料，没有执行项目构建、测试、部署或服务器探测。文件中历史测试数量和部署状态只属于原记录的版本与时间。
