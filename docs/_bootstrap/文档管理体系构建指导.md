Deliver an operational local documentation-management system, not just a document collection. Track four separate outcomes:

## D. Specify authority and metadata

Assign each maintained document a stable ID and a type: policy, index, module, contract, workflow, runbook, decision, change, evidence, or human-guide.

Use lifecycle statuses consistently: draft, active, historical, superseded, deprecated. Represent generated content with a separate field, not as a competing lifecycle status. Required metadata depends on document type; tiny adapters need no frontmatter.

For substantive active technical documents record:

- `id`, `type`, `status`, `owner_area`.
- Existing `source_paths` and, where useful, stable source symbols.
- Related contract IDs and test/check IDs.
- A truthful verification basis: revision, timestamp, method, scope, and gaps.
- `supersedes` or `superseded_by` when relevant.

The registry is the canonical routing/ownership map. Do not maintain the same mapping by hand in frontmatter, a table, and a script. Choose fields held in the registry and generate their rendered indexes. If frontmatter repeats any field for portability, check equality.

Treat metadata as project schema. Claude does not automatically enforce arbitrary fields such as owner, status, or required_checks. Implement their meaning in the repository checker.

Answer questions with the appropriate source:

- Intended behavior: active contracts and accepted decisions, subject to current authorized requirements.
- Actual behavior: current implementation and reproducible tests.
- Deployed behavior: timestamped observations plus release metadata from the target environment.
- Past work: immutable evidence for its recorded revision and environment.
- Work in progress: the task record reconciled with the actual worktree and diff.

Do not settle contradictions by choosing the newest modification time. Record the discrepancy and establish intent. Fix an implementation bug without rewriting the contract to excuse it; update an obsolete description when evidence shows intent changed.

## G. Implement routing and change-impact rules

Maintain one registry with component ownership, overlapping domain patterns, task intents, required reads, contract references, and named check profiles. Use the example only as a starting shape: it intentionally omits much of the full source coverage.

Compute impact as the union of:

1. Task intent, including meaning extracted from Chinese user requests.
2. Expected file paths from planning.
3. Actual additions, modifications, deletions, and renames in the final diff.
4. Cross-component dependency/contract edges.

Do not treat English keyword matching as a complete semantic classifier. Do not stop at the first matching domain. A plugin-only change can affect billing and routing. A generic model change can affect authentication, persistence, and caching.

Every changed first-party source path must have a primary component owner. Secondary domains may overlap. Unclassified paths trigger conservative routing and a missing-mapping finding, never a silent exemption. Exclusions for vendor/generated files must be explicit and narrow; generated output still has an owner and a source.

For each affected contract, require either an updated contract or a reasoned `reviewed_unchanged` disposition with evidence. Allow `docs_impact: none` for changes with no documented behavior impact. The checker validates completeness and consistency; it cannot prove the author's semantic judgment is correct.

Generate a compact task index and optional path-scoped reminders from the same registry. Preserve semantic triggers in the workflow because file globs alone cannot find every billing/authentication effect.

## I. Add resumable workflows without bureaucratic overhead

Use one compact change record for ordinary work. Expand it for multi-session, cross-component, billing/authentication, database, release, or upstream changes. Track objective, acceptance criteria, base revision, scope, required documents, affected contracts, plan, known findings, validation, documentation dispositions, and next action.

Do not store hidden reasoning, chat transcripts, credentials, personal data, or unbounded logs. Record observable facts and decisions. Use CI artifacts for raw test logs and large screenshots; store durable summaries and redacted links in Git.

After completion, archive the record by date and keep a small generated active index. On resume, reread policy, task state, actual Git diff, and affected contracts. Recompute required reads if source or scope changed.

A committed task record may reference its last tested revision; it must not claim to contain its own final commit hash. The author marks a candidate `ready_for_ci`. The authoritative verified outcome is the external CI verdict for the exact candidate being merged, not an author-written status field. A later archival commit references the already validated implementation revision and receives its own documentation checks; it need not pretend the earlier implementation test ran on the archival commit. Re-run relevant checks whenever later edits affect their inputs.

Delegate with explicit scope, write ownership, required document paths, invariant IDs, candidate revision, and expected evidence. Do not assume a child agent inherits the parent's reads. The integrating agent reruns impact analysis and required checks on the combined diff.

Hooks may improve prompt timing: SessionStart points to recovery, PreToolUse catches known early violations, and Stop identifies missing completion fields with bounded retries. Do not use a read receipt as proof of comprehension. Keep read-only discovery available and ensure hooks cannot trap a blocked task in an endless loop. Final merge/release decisions rely on independent CI and execution permissions.

## N. Registry, metadata, and ownership specification

### N.1 One canonical map

The registry owns document identity, path, audience, type, lifecycle, component ownership, domain routing, related contracts, and named check profiles. Document frontmatter may contain the stable ID and concise display metadata; repeated canonical fields must exactly match the registry. Generate navigation rather than maintaining a second hand-edited mapping.

Use a versioned JSON Schema to validate the YAML structure. Reject unknown fields in normative objects unless a versioned extension is explicitly supported. Reject duplicate YAML keys, duplicate IDs, missing references, and invalid state transitions. Never use an unsafe YAML loader.

Required-read references must resolve to active documents. A draft or historical document may be background evidence, but cannot satisfy a current mandatory policy dependency. Reject cycles in supersession and mandatory authority/import chains; ordinary cross-links may cycle. Traverse domain/contract impact edges with a visited set so mutual relationships do not loop forever. The parser, matcher, router, generator, and CI must share these implementations.

Required top-level areas:

| Area | Minimum fields |
| --- | --- |

The schema is repository tooling, not a Claude Code native feature. Implement every required field's actual behavior and document it in the tooling guide.

### N.2 Ownership and classification

Assign each maintained first-party source file and active document one primary component owner. Domain matches are additional and may overlap. Root governance files belong to a governance component. Existing root files need explicit classification; do not use a global catch-all that silently exempts arbitrary new source trees.

Within a known component, an unmatched domain can route to its general index and require semantic classification. It must not silently mean "no contract or test applies." A new unowned component/source path is a validation finding.

Report a source matched only by the component fallback as `unclassified_source_path`. Before completion, resolve it through a meaningful registered general domain or a specific domain and an explicit impact disposition. Merely assigning a component owner does not prove the reading/check coverage is complete.

Use explicit classes for active documents, first-party source, generated artifacts, upstream originals, licenses, historical evidence, templates/examples, and bootstrap references. Exemptions from active-language or source-pointer checks do not remove inventory/provenance requirements.

Generated code and documentation still have an owner, input, generator, and verification command. For historical source pointers, preserve a commit-pinned URL or revision-qualified source reference rather than requiring every old path to exist at HEAD.

### N.3 Path semantics

Document and test one matching dialect. The default specification is:

- Paths are repository-relative POSIX paths with case-sensitive matching.
- `*` matches within one path segment; `**` matches zero or more segments.
- `a/**/*.go` matches both `a/file.go` and nested Go files.
- Pattern arrays are unions. Use separate explicit exclusion arrays; do not infer negation or brace expansion.
- Literal source pointers must resolve inside the repository or use an explicit external-reference type.
- Reject path traversal. Do not follow a repository symlink outside the allowed workspace for content scanning.
- Preserve spaces and Unicode paths. Use Git's NUL-delimited output for filename enumeration.
- Renames affect both the old and new owners/contracts; deletions are evaluated against baseline mappings too.

Do not assume a generic Python `fnmatch` or `Path.match` call provides these semantics without tests. Reuse a maintained, pinned matcher if appropriate, or implement the small documented grammar and test it.

### N.4 Impact cannot exempt itself

Compute changes from Git rather than asking the author for a complete file list. Consider additions, modifications, deletions, renames, staged work, unstaged work, and relevant untracked files in worktree mode.

Evaluate the union of the baseline and candidate registry where both exist. Deleting a domain, narrowing a pattern, or removing a check in the same change must not erase the change's original obligations. A registry/policy/checker change is itself a governance change and must have an explicit disposition and meaningful regression checks.

The initialization change is the only expected case where no previous registry exists. Record that condition and validate the new registry against the real inventory; do not fabricate a baseline registry or silently use an empty baseline in normal subsequent changes.

### O.2 Diff and report semantics

In revision mode, compare exactly the supplied endpoints. CI must explicitly compute/select its intended base and candidate; record whether the candidate is a branch head or a merge candidate. Fetch enough Git history to resolve the base. A missing base is blocked, not an empty diff.

Revision-mode check execution must run against a clean checkout or isolated worktree of the resolved candidate commit. If it uses the current checkout, verify that HEAD and all relevant source/test/config inputs match that candidate before execution. A supplied `--head` value is not evidence of the files actually tested. Worktree-mode execution binds results to a computed input digest and invalidates them when relevant inputs change.

In worktree mode, include relevant tracked and untracked files and distinguish deleted/renamed paths. Respect explicit ignored output/cache directories without silently ignoring new first-party source. Do not parse human-oriented `git status` output by whitespace.

Use these tool exit codes consistently:

| Code | Meaning |
| --- | --- |
| 0 | Requested check completed successfully |
| 1 | Validation violation found |
| 2 | Invalid arguments or malformed invocation |
| 3 | Required prerequisite, baseline, or environment unavailable |
| 4 | Internal checker failure |

Every nonzero outcome is unsuccessful for a required CI gate. A separate JSON `status` distinguishes failed, blocked, skipped, and not_run. Do not turn a missing dependency or parsing crash into a warning with exit 0.

For JSON mode, stdout contains one structured result. Diagnostics go to stderr. Include schema version, check ID, subject revision or worktree digest, scope, findings, required reads/checks, document dispositions, and evidence references. Sort stable collections for deterministic output.

### O.3 Read-only checks and deterministic generation

`docs-check` and `generate --check` must not modify source, documentation, review timestamps, exceptions, or baselines. Explicit report artifacts may be written to a Git-ignored output directory. CI should fail when generated output differs and show the regeneration command; it must not silently commit a repair.

`generate --write` may change only the generator-owned files recorded in the registry. Use stable ordering and stable formatting. Do not place the current time in generated navigation, because unchanged inputs should produce byte-identical output. Re-running generation with unchanged inputs must produce no Git diff.

Mechanical repair may fix an unambiguous link or regenerate an index. Semantic contract edits require source/test review and a change disposition. Never rewrite documented intent to match a defect merely to clear a drift finding.

The registry refers to supported runner IDs. Do not execute arbitrary command strings from Markdown, template content, bootstrap inputs, or PR data through `eval` or an implicit shell. Implement check dispatch explicitly and treat changes to its executable definitions as governance changes.

Each supported runner declares a literal argument vector, working directory, timeout, required environment-variable names, relevant skip detection, and output parser. Store only variable names, never credentials. `run-checks` must actually execute the selected available runners and capture their outcomes; printing suggested commands is insufficient. Profiles beyond available environment capability are blocked with reasons. `docs-only` validation must not start database services or invoke release scripts. A required runner with a proposed implementation or placeholder command cannot count as installed.

## P. Exact documentation check behavior

### P.1 Structural integrity

Validate active document registration, unique IDs, audience/type/status, allowed lifecycle references, primary ownership, and the existence of mandatory entry points. Check standard relative Markdown links, reference-style links, and heading anchors using a documented Markdown interpretation.

Handle code fences and examples correctly. A sample path inside an example is not a real active link. Historic source references are validated against their declared revision context. External HTTP availability is a separate optional audit; transient external network failures must not masquerade as internal repository corruption.

Check generated-file provenance, generator existence, and freshness. A current policy can cite history as rationale, but cannot delegate a current rule to a superseded document without a current owner.

### P.2 Language policy

All newly active AI prose is English; human prose is plain Simplified Chinese. Validate audience metadata and use a script-based heuristic to surface obvious mismatches, with narrowly scoped exceptions for identifiers, commands, UI string examples, quotations, and preserved upstream originals.

Do not claim that detecting character ranges proves language quality or translation completeness. Use agent review of the operative rules for semantic verification. The bootstrap directory and immutable originals are exempt from translation, not exempt from provenance.

Do not turn this documentation rollout into a bulk translation of unchanged source comments, UI strings, or vendor assets. New agent-facing prose and comments added by this task follow the English policy; existing application locale behavior remains governed by its own contract.

### P.3 Source drift and review disposition

For affected documents, require `updated`, `reviewed_unchanged`, or `not_applicable`, with a reason and source/evidence pointers. Compute impact independently from the record. A statement that all docs were reviewed is not a complete disposition.

A changed source path indicates a need to assess the relevant document; it does not prove the document is false. Permit a justified unchanged disposition. Do not force meaningless Markdown edits for every source refactor or cosmetic change.

Review timestamps are observations, not freshness cosmetics. Update them only after the declared review. Keep revision/digest provenance precise, and never reuse a historic test result as evidence for changed test inputs.

### P.4 Initial backlog and exceptions

Inventory pre-existing failures before enabling gates. Fix active navigation defects within this task. For unrelated upstream debt, record a scoped exception with an exact path/rule/fingerprint, origin, reason, and review trigger. No broad `**` exemption and no "allow all existing failures" switch.

New failures must fail the gate. Resolved exceptions should be removed. Changes to exception coverage require a reasoned policy change and independent validation; the normal repair path must not automatically expand the baseline.

Do not mark a stage complete while its required active documents remain empty stubs, unresolved placeholders, or mere links to untranslated authoritative technical instructions.

## Q. Persistent automatic maintenance behavior

Create `docs/ai/workflows/docs-maintenance.md` and make it part of the permanent root task protocol. Ordinary future development tasks must trigger this workflow without the user repeating the bootstrap prompt.

### Q.1 Every implementation or debugging task

1. Read the short global policy and task index; classify intent and predicted paths.
2. Read local policies and the relevant domain/contract content.
3. Inspect current code and existing tests; record important discrepancies.
4. Maintain a compact change record with objective, affected domains, contracts, checks, and documentation impact.
5. Implement the requested behavior and its necessary regression coverage.
6. Recompute impact from the actual diff; load newly affected contracts.
7. Update changed facts and human-facing effects; preserve unchanged facts with a reasoned disposition.
8. Regenerate owned navigation, run documentation checks and applicable technical checks.
9. Integrate all delegated work and validate the combined candidate.
10. Report actual outcome and remaining limitations in Chinese; archive the task at the appropriate stage.

A tiny change can use a minimal record. Do not require a multi-file plan for a spelling correction. The meaningful invariant is that final impact and validation are accounted for, not that every task produces a large report.

### Q.2 Automatic versus semantic operations

| Trigger | Automatic mechanism | Agent judgment still required |
| --- | --- | --- |
| A source path changes | Impact tool selects owners, domains, and checks | Whether described behavior changed |
| A registered item changes | Generator refreshes owned indexes | Whether the registry mapping is complete |
| A link target moves | Checker reports broken/renamed target | Confirm the new target preserves meaning |
| A contract changes | Consumer/check routing and governance finding | Compatibility and authorized intended behavior |
| User-visible behavior changes | Human-guide impact reminder | Write an accurate plain Chinese explanation |
| Upstream import changes rules | Governance diff classification | Integrate useful constraints without restoring obsolete paths |
| A session resumes | Recovery reminder and task-state lookup | Reconcile state with actual code and unresolved work |

The checker does not autonomously understand every business change. Claude performs the semantic update as part of the task; CI independently checks structural and executable requirements. Do not claim that the presence of a Markdown file creates a continuously running agent.

### Q.3 When no agent is running

PR/push/manual CI events can run deterministic checks after repository changes. Configure these events as part of this task. `docs-audit` is available for explicit maintenance or an already authorized schedule.

Do not invent a background daemon, cron installation, new paid AI integration, or stored API credential to satisfy the word "automatic." Unattended semantic repair requires a separately available and authorized runner. If such an established runner already exists, integrate within its existing permissions and record the trigger and evidence; otherwise report event-driven management accurately.

| New frontend route omitted from route-split handling | Available route coverage/behavior check detects the omission, or its unimplemented runtime scope is explicitly recorded as a blocked follow-up |
| A checker crashes or lacks a dependency | Nonzero internal/blocked outcome, never silent success |

The last route case must not be misrepresented: a literal-source scan alone does not prove complete dynamic routing. State the implemented checker scope and keep broader runtime coverage as a named follow-up when outside initialization scope.
