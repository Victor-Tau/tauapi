# Contract title

## Scope and authority

State the intended behavior and participating components. Identify canonical
machine-readable data where it exists. Do not duplicate an exhaustive generated
catalog in prose. Separate current guarantees from proposed improvements.

## Normative behavior

| Invariant ID | Trigger or input | Required behavior | Verification anchor |
| --- | --- | --- | --- |
| REPLACE-001 | Concrete condition | Observable result or preserved property | Source/test/profile |

Use MUST for actual obligations, SHOULD for justified defaults, and MAY for
options. Define exceptions explicitly. Do not invent a guarantee based only on
a happy-path test.

## Edge cases and failures

Cover applicable missing/invalid inputs, limits, concurrency, retries, partial
success, cancellation, timeouts, caching, and compatibility boundaries. Omit
categories that do not apply instead of filling them with boilerplate.

## Change procedure

List required consumer changes, generated artifacts, fixtures, and documentation.
Explain compatibility and rollout implications. An incompatible change needs a
decision and migration strategy, not just an edited assertion.

## Validation and evidence

Name existing tests and required profiles. Distinguish a static review from a
runtime or end-to-end check. List gaps and explain what would establish each
remaining guarantee.
